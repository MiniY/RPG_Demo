# RPG_Demo 技术追问与压力面试

## 1. 使用方式

先口头回答，再展开参考要点。压力面试不是追求“完美”，而是观察：

- 是否承认未知；
- 是否保持事实边界；
- 是否能提出验证方法；
- 是否能在质疑下守住状态所有权和不变量。

## 2. “大量代码是 AI 写的，这项目为什么能算你的？”

### 稳健回答

> 我不会用代码行数主张所有权。这个项目对我的价值是：我提出和收敛需求、选择边界、做真实场景验收、发现问题、要求回归，并逐步掌握关键链路。AI 大量辅助了实现，所以我只对自己能解释、定位、验证和修改的部分负责。如果现场让我改一条放置规则、加一个存档校验或分析时序 Bug，我会用这种能力证明，而不是用“都是我写的”证明。

### 追问：那架构也是 AI 决定的吧？

> 具体方案常由 AI 提议，我参与约束和验收。作者归属无法逐行重建，所以我不会说完全由我原创。我能说明为什么最终保留 Plan/Commit、GenerationId 和入口检查点，以及替代方案的代价；如果不能说明的部分，我会明确标为正在学习。

## 3. “你的项目是不是过度设计？”

答：

> 局部可能存在复杂度偏高，例如大型编排类和多层兼容校验。但随机地图整合确实有旧世界保留、对象占位冲突、异步迟到和半初始化等真实问题，因此生命周期与 Generation 不是纯粹装饰。判断过度设计要看它是否保护已发生的故障和明确不变量。对于背包小规模 UI，全量重建就可能是暂时合理的简单方案，我不会为了形式统一立即改成复杂虚拟化。

## 4. “为什么不用现成地图插件？”

答题方向：

- 项目定位包含学习生成、测试和整合；
- 自研使 Seed、不变量、对象放置和 TowerRun 兼容性可控；
- 商业项目应评估插件成本；
- 不否认插件在工具、性能、编辑器体验上的优势。

避免贬低现成方案。

## 5. “相同 Seed 为什么还要保存 Generator Version？”

> Seed 只初始化随机序列。算法步骤、调用顺序、阈值或配置改变都会改变结果。Generator Version 与配置身份共同说明“用哪套规则解释 Seed”，否则旧检查点可能生成不同地形，玩家状态却被应用到错误世界。

## 6. “为什么不把生成结果整张存下来，省得版本不兼容？”

可以权衡：

- 保存完整 MapData 可提高精确恢复；
- 文件更大，Schema 更复杂；
- 仍需迁移对象配置；
- 不能解决所有语义对象版本变化；
- 当前入口重建策略更简单。

`【建议方案】` 若需要跨大版本长期存档，可保存 compact MapData snapshot 或提供 migration，不是无条件继续只存 Seed。

## 7. “你说事务，为什么没有数据库？”

> 事务是语义，不限数据库。商店一次购买涉及金币、商品、库存；我需要原子性和一致性，所以捕获快照、应用候选、失败回滚。当前主线程本地执行，不提供数据库式并发隔离；磁盘持久性由 TowerRun Store 单独处理。

## 8. “`GameSaveService` 叫 Save，为什么不落盘？”

> 这是演进后的命名债务。早期承担旧保存语义，TowerRun 引入明确检查点后，它保留为旧调用者的内存事务接缝。当前注释已明确不读写旧 `save.json`。我会优先用 ADR 和调用迁移后再重命名，而不是只改类名造成更大混乱。

## 9. “SHA-256 能防作弊吗？”

> 当前 Hash 用于内容一致性/写后验证，不是安全签名。攻击者可同时修改 JSON 和 Hash。防篡改需要密钥签名、平台安全存储或服务端权威，但单机游戏也要权衡威胁模型。

## 10. “原子替换就绝对不会坏吗？”

> 不是。原子性取决于文件系统和 API；断电、磁盘、杀毒软件、外部进程和平台差异仍存在。项目通过临时文件、备份、复读和 uncertain 分类降低风险，但不能宣称绝对 durability。

## 11. “为什么 TowerRun 不直接重载场景？”

> 重载场景只解决对象重建，不自动解决 Seed、入口记录、Session、Slot、Generation、Gate 和对象池语义。当前地图运行时生成，Coordinator 需要控制数据应用和 Ready 边界。场景重载可以成为实现手段，但仍需同一套流程契约。

## 12. “怪物为什么不用 NavMesh？”

回答应基于实际：

- 当前 2D 地图和 AI 使用较轻量移动/感知；
- 地图有可走性逻辑但不是复杂 NavMesh 代理；
- 若障碍复杂、追逐需绕路，当前直线 Chase 会不足；
- 可选 Grid A*、A* Pathfinding Project 或 2D NavMesh；
- 先用失败场景和性能数据决定。

## 13. “每次攻击 FindObjects，不是很差吗？”

> 它不是每帧，而是每次攻击。小规模原型可能足够，但扩展后应 Profiler 验证。替代包括 NonAlloc Physics 查询、当前房间 Registry 或空间索引。我不会在未测时声称这是性能瓶颈，也不会否认它的可扩展性风险。

## 14. “你有 216 个测试，所以质量很好？”

> 数量不等于质量。我会说明覆盖层次和限制：216/216 对应特定提交的 MapGeneration EditMode；另有 PlayMode、GPU 和跨进程测试。TowerRun EditMode 还存在 Runner 挂起，视觉手感也需人工。质量结论要看是否覆盖关键不变量和故障，不是只看数字。

## 15. “测试为什么会挂起？你连原因都不知道？”

> 当前能确定的是断言和 XML 完成，但进程未退出；原因尚未被证据锁定。我不会把猜测当结论。下一步会 fixture 二分、检查静态订阅/Editor callback/异步资源、比较最小项目，并把进程退出作为独立验收条件。

## 16. “迷雾 Bug 为什么测试之前没发现？”

> 原测试更关注地图数据和最终显示，没有观察 `MapGenerated` 到玩家 spawn 之间的瞬时时序。真实 Run 暴露后加入探针和定向回归。教训是测试要围绕完成边界和事件顺序，而不只是最终静态状态。

## 17. “为什么 UI 不直接读存档？”

> UI 应投影当前运行时权威状态。磁盘记录是恢复边界，不是每帧交互源。让 UI 直接读文件会引入延迟、缓存不一致和错误的职责耦合。

## 18. “红点这么简单也算功能吗？”

> 当前只是会话级提示规则，我会准确称为简化红点，不称为完整未读系统。文档还给出了逐物品序列和 last-seen 的扩展设计。

## 19. “如果 Slot 写入时程序崩溃怎么办？”

答题点：

- 正式文件之前有旧版本；
- 新数据先写/验证 temp；
- replace/backup；
- 下次 Read 分类；
- 如上次结果不确定，通过 token/内容观察；
- 无法保证断电级绝对安全。

## 20. “如果同一槽被两个进程同时写呢？”

`【当前边界】` 跨进程测试验证读写持久化，不等于实现多写者并发控制。可选方案：

- 文件锁；
- lock file + PID/超时；
- OS named mutex；
- Compare-And-Swap token；
- 单实例应用约束。

在没有实现前不能说支持多写者。

## 21. “如何让地图生成不卡主线程？”

回答步骤：

1. 先分解并测 Generate/Plan/Project/Materialize。
2. 纯 C# 数据生成可考虑后台线程/Jobs。
3. Tilemap、GameObject、Unity API 回主线程。
4. 分帧投影需要加载态和取消语义。
5. GenerationId 防止任务完成时已过期。
6. 保持 deterministic input。

## 22. “如果让我现在删掉一半架构，你删什么？”

好的回答不应任意删核心不变量。可以说：

- 保留 MapData、Generation、Plan/Commit、Slot 校验；
- 优先合并重复适配器、减少 UI 运行时构建复杂度；
- 把只被一个调用者使用且没有独立策略的薄封装收回；
- 用依赖图、测试和修改频率决定，不按文件数决定。

## 23. “你最不确定的地方是什么？”

可诚实回答：

- 当前全量测试未在最终工作树重跑；
- TowerRun EditMode 退出挂起；
- 设置 UI 已由 v4 收口到未提交 v6，但尚未获得用户最终视觉批准或提交授权；
- 地图/背包性能缺少量化；
- 个人对部分 AI 生成实现仍需闭卷复现。

然后说明核实计划。

## 24. “如果面试官让你现场改功能怎么办？”

建议路径：

1. 先说出状态所有者和不变量。
2. 搜索入口和现有测试。
3. 先加一个失败用例或最小复现。
4. 小步修改。
5. 跑定向测试。
6. 说明未覆盖边界。

这比直接背完整类更能证明真实能力。

## 25. 压力面试自评表

每题 0～2 分：

- 0：只能说结论。
- 1：能讲机制，但没有项目证据或边界。
- 2：机制 + 代码入口 + 失败路径 + 验证 + 局限。

不要把自评分写成正式掌握度；只有实际口头/现场表现才是证据。
