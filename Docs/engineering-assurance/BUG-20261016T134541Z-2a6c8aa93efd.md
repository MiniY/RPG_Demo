## 假设与最小实验

按当前证据排序，尚未将假设写成事实：

1. 原生网络 job 在 JobSystem 关闭时未完成：预测本轮当前栈重现主线程等待与 Curl worker。
2. Test Framework 或 Smoke 路径特有的退出问题：预测同快照的直接 Exit 用例能自然退出、Smoke 仍失败。
3. 内建服务或包请求的生命周期问题：需要当前栈和请求归属证据；Snapshot 的 `UnityConnectSettings.asset` 已为 `m_Enabled: 0`，不能重复关闭服务充当修复。
4. Supervisor 环境影响：历史先于 Supervisor 的相同等待链降低其优先级；本轮不以绕过门禁启动作对照。

最初协调最多先做两个用例：

- 同一冻结 Snapshot 的新 Sandbox，只注入有 PID/project/UTC 标记的 Editor 静态诊断方法，通过 `-executeMethod` 请求 `EditorApplication.Exit(0)`；NUnit 为 NOT_RUN。
- 仅当第一项自然退出时，再用独立 Sandbox 复现原 Smoke；保持原测试断言、原超时与共享执行器。

执行中 DataTest 聊天收到用户追加的 A/B/C 对照要求，上限为三组：直接退出、最小 EditMode、原 Smoke。因此第二项先加入最小 EditMode 对照，最后一组用于原 Smoke 当前栈。另行提出的 P0 生命周期扩展不改变本聊天的 Supervisor 冻结边界。

退出请求或 XML 出现后 10 秒仍存活才采集当前栈；每次先核对本次 owned PID/创建时间，使用微软签名 CDB、本地 PDB、短采集期限和 `qd` 分离。采集模式、可能暂停、错误、采集本身耗时均独立记录。调试器采样不能被写成零干扰。

微软文档说明 [`-pv` 非侵入调试会暂停线程](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/noninvasive-debugging--user-mode-)；[`-pvr` 与其类似但不暂停目标](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/cdb-command-line-options)；[`qd` 分离并保持目标运行](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/ending-a-debugging-session-in-cdb)。运行中读取的各线程栈不是同一瞬间的原子快照；具体参数组合是否可用仍以本机实际日志为准。

### submit、abort、移除、FinishDoRequest 与交接顺序

本次 560 bytes 的实际代码已经离线解析为 188 条指令（包含有界范围中的邻接入口及 padding，不能都算作同一函数）。`runtime-code-review.json` 保留原 bytes SHA 与指令；旧同 build 的实际 CurlExecute/DoRequest/FinishDoRequest 指令继续复用。

1. **submit 静态路径**：DoRequest 设置 parent+0x88，向 pending 追加，再在需要时调度 Curl job。重复提交的具体调用者、次数和时间未直接采集。
2. **加入 active 静态路径**：`curl_multi_add_handle` 返回 0 或 7 都跳至追加路径；该路径增加 active count 并写入 transport 指针，没有在这段路径做重复成员检查。[官方 libcurl 错误码](https://curl.se/libcurl/c/libcurl-errors.html)把 7 定义为 `CURLM_ADDED_ALREADY`。本 Run 没有逐调用返回值，不能声称已观测到返回 7。
3. **abort 静态路径**：TransportCurl::Abort 写 +0x08；BackendAbortAll 设置后端标志并等待 job。这里没有函数事件记录，实际调用时刻仍 UNKNOWN。
4. **正常完成静态路径**：读取 CURLMSG_DONE → remove easy → 查找首个匹配 transport → active count 减 1、末项替换该槽 → FinishDoRequest。它只移除一份匹配项。
5. **完成交接静态路径**：FinishDoRequest 读 parent+0x88、处理 raw+0x118/PostRequest，再调度父请求 job。动态状态变化与此相容，不把它当作准确 callback trace。
6. **Cleanup/析构静态路径**：本次实际代码中，Cleanup 在 RVA `0x1772402` 调用 easy_cleanup、`0x1772407` 清 easy 字段；deleting destructor 也清 easy，随后 `0x17721ab/0x17721b2` 改为基类 vtable，再按条件 delete。本 Run 的持续项一直匹配派生 TransportCurl vtable，因此不能套用“基类析构脚印”或声称 delete 已执行。
7. **退出等待机制**：active 非空、running handles 为 0、abortAll 为 0 时，旧同 build 的 CurlExecute 指令仍允许继续循环；这与本次持续遗留槽位、旧双份 JobSystem 等待栈相容。

**已确认的近因事实**是重复 active 成员及后续 null-easy 遗留条目；“重复入队经过返回 7 路径、完成只移除一份，从而遗留”是有直接状态及静态代码支持的具体因果解释，但 API 返回和逐函数事件没有被追踪。重复 submit 的上游发起者、是否存在重入/重试、精确取消与回调时序仍 PARTIAL / UNKNOWN。不能将它扩写为所有历史 Run 的统一已证实根因。
