## 1. 先建立正确心智模型

随机地图不是“随机选 Tile 画到 Tilemap”。项目真正处理的是三个不同问题：

1. `Generation（生成）`：产生一份符合规则的逻辑地图。
2. `Integration（整合）`：让玩家、相机、怪物、商人等系统进入这份地图。
3. `Presentation（表现）`：把逻辑地形、装饰、迷雾和标记显示出来。

如果混为一个步骤，就很难回答：

- 地图画了一半失败怎么办？
- 怪物位置是否合法？
- 新地图失败时旧地图要不要消失？
- 小地图与 Tilemap 不一致时谁才是真相？
- 旧一代异步回调为什么不能影响新一代？

玩家在游戏里感受到的不是这些内部阶段，而是：每次进入楼层会得到可复现但有变化的地图；出生、怪物、商人、装饰、小地图和相机同时正确；Commit 前的生成失败不会预先清空当前 Active 地图和 Registry。需要注意：在 TowerRun 流程中，操作 Gate 可能仍会把玩家留在 `Failure` 界面并阻止继续操作，因此“旧世界数据未被替换”不等于“玩家一定可以继续游玩旧世界”。

## 2. 核心数据结构

### 2.1 `MapGenerationSettings`

它描述生成参数，例如尺寸、Seed、噪声和路径约束。生成器克隆设置并为不同 attempt 派生 Seed，避免重试篡改调用者原始配置。

### 2.2 `MapData`

`MapData（地图逻辑数据）` 是地形和可走性的逻辑真相。Tilemap、小地图、出生与对象放置都应从它派生，而不是互相读取表现结果。

精确意义：

- Tilemap 是 `Projection（投影）`，不是业务状态源。
- 小地图不是摄像机截图。
- 可走性不应通过“某个 Tile 看起来像草地”临时猜测。

### 2.3 `MapPlacementPlan`

放置服务先输出 `MapPlacementReservation（地图放置占位）`：

- Logical ID
- Role
- 目标单元格
- 占用单元格
- Scene-bound/Generated 等所有权

所有占位通过后，计划才提交并 materialize（实体化）到真实世界。

### 2.4 `MapObjectRegistry`

Registry 记录本代语义对象。它使其他系统不必用模糊的 Tag、名字或全场景搜索来猜：

- 哪些怪物属于当前层；
- 出口标记对应哪一代；
- 某对象占用哪些格子；
- 对象是场景预置还是本代生成。

## 3. 生成算法流水线

`RandomMapGenerator.Generate()` 的主要过程可概括为：

```text
输入 Settings
  ↓
生成 Height / Moisture / Temperature 三类噪声
  ↓
按阈值分类地形
  ↓
清理过小或不合理区域
  ↓
处理边界
  ↓
建立 Spawn Protection
  ↓
从出生区域构造通往边缘/出口方向的路径
  ↓
移除不可达区域
  ↓
应用地形嵌套规则
  ↓
扩宽通道并保证至少 2 格/2×2 净空约束
  ↓
重新检查嵌套和语义一致性
  ↓
输出 MapData
```

### 为什么需要多个噪声通道

单个 Noise（噪声）只给出一维标量，很难表达“高、湿、冷”等组合语义。多个通道允许把地形理解成环境条件的组合，而不是简单色带。

### 噪声不保证可玩

噪声只产生空间分布，不自动保证：

- 出生点可走；
- 出生区域与出口连通；
- 通道足够宽；
- 语义对象有合法位置；
- 不会出现细碎孤岛。

因此后处理和验证不是“优化项”，而是生成正确性的一部分。

## 4. 确定性

`Determinism（确定性）` 指相同输入、相同算法版本和相同配置身份应得到同一逻辑结果。

它的用途：

- 用 Seed 复现 Bug。
- 测试比较稳定结构。
- TowerRun 检查点不必序列化整张 Tilemap。
- 玩家可以分享地图 Seed。

### 确定性的边界

仅保存 Seed 不够，还需考虑：

- 生成器版本；
- 配置身份；
- 随机调用顺序；
- 浮点和平台差异；
- 后续放置算法版本。

因此 TowerRun 存档检查 `generatorVersion` 与 configuration identity，而不是看到一个 Seed 就盲目恢复。

## 5. 运行时生命周期

主要 Phase：

```text
Initialized
→ Preparing
→ Generating
→ Planning
→ Planned
→ Committing
→ Committed
→ Projecting
→ Materializing
→ SpawningPlayer
→ Reinitializing
→ BindingCamera
→ ValidatingRuntime
→ Ready
```

失败可能发生在多个阶段，但语义不同。

### Commit 之前

候选地图还没有成为正式世界，可以使用派生 Seed 重试。源码和 EditMode 测试直接保证的是：Commit 前不会替换当前 Active Map/Plan/Registry，也不会退役旧 Registry。上层 TowerRun 是否允许玩家继续操作，还取决于 Coordinator 的 Failure 状态与 Gate，不应从底层数据保留进一步推导出“仍可自由游玩”。

### Commit 之后

Registry 和逻辑世界已经切换。若投影/实体化失败，不能简单把同一流程当作纯生成失败继续重试，否则可能同时存在：

- 新逻辑地图；
- 旧画面；
- 部分已移动对象；
- 错误的玩家位置。

项目因此把 post-commit failure 视为需要明确失败处理的状态。

## 6. `MapIntegrationOrchestrator`

它是整合的策略编排器，而不是 Unity 表现组件。主要职责：

1. 为每次尝试创建候选 Generation。
2. 调用生成委托产生 `MapData`。
3. 调用规划委托收集 Reservation。
4. 验证 pending/active Generation ID。
5. 提交地图、计划和 Registry。
6. 调用投影。
7. 返回结构化结果。

### 为什么使用委托/接口边界

这样可在测试中用轻量 fake：

- 让第 1、2 次失败，第 3 次成功；
- 构造计划冲突；
- 模拟过期 Generation；
- 验证 commit 前后行为；
- 不必加载完整场景和 Tilemap。

这体现 `Deep Module（深模块）` 思想：调用者面对的是一次整合操作，内部吸收重试、验证和提交复杂度。

## 7. 语义对象放置

以 Monster Placement 为例：

1. 验证场景中恰有预期的 scene-bound Monster。
2. 遍历候选可走单元格。
3. 检查地形类型。
4. 检查与 Spawn 的路径步数范围。
5. 检查占位冲突。
6. 用稳定评分选择候选。
7. 把 Reservation 加入 Plan。
8. Commit 后将准确的对象移动到目标位置并绑定 Registry。

Merchant、Animal、Plant、Destructible 复用同一种“Plan → Materialize”接缝，但策略不同。

### 这个设计解决什么问题

如果每个组件在 `Start()` 中各自找随机位置：

- 它们可能抢同一格；
- 顺序改变会改变结果；
- 无法一次性验证整张地图；
- 失败时对象已经移动；
- 测试难以稳定复现。

## 8. 玩家、重初始化与相机

地图生成后不能只改玩家 `transform.position`。依赖世界坐标/边界的系统也必须更新：

- canonical player 出生；
- 需要 reset 的玩家动作/控制器；
- 可能缓存地图或目标的组件；
- Cinemachine follow/Confiner 边界；
- 小地图当前代；
- TowerRun finalizer。

`MapDependentReinitializationService` 通过 `IMapTransitionResettable` 等边界重置依赖者，避免控制器保留上一层的瞬时状态。

## 9. 小地图与迷雾

### 数据驱动

小地图根据 `MapData` 构造纹理/显示，而不是读取 Tilemap Renderer 的屏幕输出。好处：

- 不受摄像机和缩放影响；
- 地形语义清楚；
- 易于添加标记；
- 可在地图尚未完全表现时准备逻辑。

### Fog of War（战争迷雾）

探索状态以布尔数组等逻辑数据保存，`LateUpdate` 根据最终玩家位置更新可见区域。

### 真实时序 Bug

`【已验证事实】` 新冒险后曾出现旧位置已探索。诊断探针发现：

- `MapGenerated` 回调时玩家还在旧位置 `(62,62)`；
- 新出生位置为 `(32,32)`；
- 回调期间提前揭示了 37 个单元格。

根因不是 Seed 错误，而是“地图事件发布时机”和“玩家最终出生时机”错位。修复后定向测试 1/1、TowerRun flow 4/4。

可迁移经验：

> 事件名称听起来像“完成”不代表所有观察者依赖的后置状态都完成。需要定义 Completion Boundary（完成边界）。

## 10. Authority 与失败保留

`MapRuntimeBootstrap` 显式选择：

- `RandomGenerated`
- `LegacyStatic`

两种权威必须互斥，不自动偷偷修复配置。

为什么不自动 fallback：

- 自动 fallback 会让测试“看似能玩”但实际上走错模式；
- 两套碰撞/对象可能同时生效；
- 错误变得静默、难诊断。

`【已验证事实】` 新 Generation 在 Commit 前失败时，当前 Active Map/Plan/Registry 保持原值，旧 Registry 不会被退役，而不是先销毁再尝试。若失败发生在 Commit 后，则属于 post-commit failure；当前架构会进入明确失败状态，但没有承诺自动恢复完整旧世界。TowerRun 同时持有操作 Gate，所以这里验证的是“旧世界状态未被预先替换”，不是“失败时玩家仍可继续控制角色”。

## 12. 性能与优化

`【待确认】` 当前没有保留完整的生成耗时、P95、GC Alloc、地图尺寸扩展曲线，不能声称已性能优化。

建议按顺序测：

1. `RandomMapGenerator.Generate` 纯 CPU 时间。
2. Plan 各服务候选搜索时间。
3. Tilemap 写入时间。
4. 小地图纹理生成与上传。
5. Materialize/Instantiate/对象池取用。
6. 首帧和 GameplayReady 总耗时。

可能方案：

- 把纯数据生成放入 Job/后台线程前，先确认是否真是瓶颈；Unity Object API 仍必须回主线程。
- 批量 Tilemap 更新，减少逐格调用。
- 缓存候选索引，避免每个放置服务全图扫描。
- 分帧投影或加载屏幕，但必须重定义 Ready 和失败语义。

## 13. 面试讲述与追问

### 13.1 1 分钟版本

> 随机地图先用 Seed 和配置生成 `MapData`，再经过连通性、出生保护、道路、嵌套和通道净空处理。商人、怪物等先输出 Reservation，统一验证占位与可达性，全部通过后才 Commit。之后才写 Tilemap、移动对象、出生玩家、重置依赖和绑定相机；最终验证成功才发布 GameplayReady。GenerationId 隔离上一张地图的迟到回调，候选失败则保留当前世界。

### 13.2 3 分钟实现思路

按四层讲：  
1. 纯数据生成：三类噪声与可玩性后处理。  
2. 全局规划：每类对象产生 Reservation，Registry 记录身份与占用。  
3. 运行时生命周期：Commit 前可重试，Commit 后进入投影/实体化/出生/相机。  
4. 正确性：Authority 互斥、GenerationId、防旧世界破坏、EditMode/PlayMode 分层测试。  
最后主动说明当前缺少量化性能数据，异步/分帧仍是建议。

### 13.3 技术细节深挖入口

- `MapIntegrationOrchestrator.Execute()` 的 attempt loop。
- `MapLifecycleTransitions` 的合法状态边。
- Monster Placement 的候选过滤与稳定评分。
- Commit 前后错误语义。
- `MapGenerated` 与 GameplayReady 的完成边界差异。

### 为什么不直接随机移动对象？

因为放置不仅是位置问题，还涉及冲突、可达性、确定性、失败回滚和代际所有权。先规划可以在改变世界前验证全局一致性。

### 为什么需要 GenerationId？

Unity 中事件、协程、动画和延迟回调可能晚到。GenerationId 相当于 version token，接收者据此拒绝旧一代结果。

### 为什么 MapData 是状态源？

如果 Tilemap 是唯一状态源，逻辑测试、存档、路径判断和小地图都要反向解释表现资源，导致脆弱耦合。

## 15. 2026-10-14 增量：地形派生 Monster / Destructible 群系

【已验证事实】新游戏使用 `ecology-v1`：`MapGenerationController.BuildPlacementPlan()` 在静态占位、Merchant 和 SweetPotato Plant 后调用 `MapEcologyPopulationService.Plan()`，再放 Animal；旧 `default` 仍使用原 Monster→Destructible→Animal→Plant 顺序。两个配方都进入同一个 `MapPlacementPlan`、`MapObjectRegistry` 和生命周期管线。源码在 `Assets/Scripts/MapGeneration/MapGenerationController.cs` 与 `MapEcologyPopulationService.cs`，配置是 `Assets/ScriptObjects/MapGeneration/MapEcologyProfile.asset`。

【已验证事实】`MapPopulationRegionQuery` 从出生点可达 Cell 和相同地形的四向连通片构造共享区域；`MapEcologyPlacementPolicy` 按 species 权重、稳定评分、合法中心和聚集半径选格。Monster 与 Destructible 共用区域/占位/安全区查询，数量、地形掩码、间距和聚集半径分别配置。目标数由可达面积除以 `cellsPerSpawn` 后限制在最低数和上限之间；有限候补仍不足最低数时明确失败，部分不足则记录 underfill。Destructible 的候选阻挡还会验证出口与所有 Monster 的可达性。

【已验证事实】`.codex/TestResults/ecology-fixed-seeds-r5-20261014.xml` 在 Unity PlayMode 对五个固定 Seed、同 Seed 重放、不同 Seed 差异、2–5 只 Monster、4–8 个 Destructible、局部聚集、登记、可达性与死亡后立即重建为 1/1 PASS，runner exit 0。`.codex/TestResults/ecology-map-regression-suite-20261014.xml` 为旧地图夹具 13/13 PASS。静态基线、注册和 PlayMode 断言不代替真实屏幕观感、长期性能或独立 Player Build。

面试可这样解释：生成器先算 `MapData`，Population 只读取逻辑地形和规划占位；先把实体位置加入计划再实例化，才能在提交前检查冲突。用可编辑 Profile 表达“哪里能出现、占比多少、最多几个”，比在 `MapGenerationController` 中硬编码 Prefab 路径更容易调参、测试和按存档版本复现。需要注意“稳定 Seed”还隐含“同 Profile、同配置、同算法版本”，否则仅 Seed 相同并不能保证同图。

【待人工确认】三类怪物与三种 Mushroom 的屏幕聚集观感、特殊地形边缘的实际 Collider 接触，以及长时间运行帧率。Merchant Population 仍是后续工作。
