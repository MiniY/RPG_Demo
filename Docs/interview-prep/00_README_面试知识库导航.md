## 1. 这套文档解决什么问题

这不是一份“功能列表”，而是一套可追溯的项目知识体系，目标有四个：

1. 能在 1～5 分钟内准确介绍项目，不夸大、不遗漏关键技术。
2. 能沿真实代码链路解释“为什么这样设计、数据怎样流、失败怎样回滚”。
3. 能用具体故障、测试和 Git 历史回答追问，而不是背诵术语。
4. 明确区分已掌握、待复习、待验证和仅建议的内容，避免把“看过代码”误当成“能独立实现”。

## 2. 证据标签

全文统一使用以下标签：

| 标签 | 含义 | 可否在面试中作为确定事实 |
|---|---|---|
| `【已验证事实】` | 由当前源码、场景、Prefab、项目配置或测试结果直接支持 | 可以，但应说明验证范围 |
| `【历史记录】` | 由 Git 提交、开发日志、Obsidian 总结或旧测试记录支持 | 可以，需说明时间点 |
| `【推断分析】` | 根据多处证据得出的工程判断 | 可以讨论，但要说是分析 |
| `【建议方案】` | 尚未落地的优化或扩展方案 | 不可说成已实现 |
| `【待确认】` | 缺少人工验收、最新全量测试或作者归属证据 | 不应下确定结论 |

## 5. 一分钟使用规则

- 面试陈述优先用“我能指出代码入口、状态所有者、失败路径和验证证据”的内容。
- 对 AI 辅助实现，使用“我负责需求边界、方案选择、验收与复盘；具体代码由 AI 大量协助生成”的诚实表述。
- `GameSaveService` 当前是内存事务镜像，不是旧 `save.json` 的磁盘持久化；真正的磁盘存档是 `TowerRunSlotStore`。
- 旧文档中“随机地图尚未整合主场景”是历史状态；当前已整合到 `SampleScene`。
- 设置界面从 v4 继续收口到当前未提交工作树的 v6；已有 6/6 定向回归、Player 构建和 1024×576/1280×720/1920×1080 截图证据，但尚未获得用户最终视觉确认或提交授权，不能说成已合并成品。
- 自动化通过不等于画面、手感、音频和完整人工游玩均已验收。

## 6. 面试表达的最低证据标准

一个技术点至少能回答以下四问，才适合列为“熟悉”：

1. 入口在哪里？
2. 谁拥有状态？
3. 正常路径和失败路径分别怎样流转？
4. 如何验证？

如果只能指出类名或复述注释，应表述为“了解/正在复习”，不应表述为“熟练掌握”。

## 7. 维护规则

- 每次重要合并后，先更新 [[15_RPG_Demo_证据索引与待核实问题]] 的快照，再修改专题结论。
- 历史事实保留时间点，不用新状态覆盖旧过程。
- 新功能必须同时记录：入口、状态所有者、不变量、失败处理、测试和人工验收。
- 本目录是面试知识库的唯一权威源；Obsidian 镜像目录是 `D:\Obsidian-1.9.14\MyObjects\Unity\RPG_Demo文档\面试复盘文档`，只接受 Source → Destination 单向同步，不在镜像中独立维护同名文件。
- 每次新增、修改、删除或重命名本目录文件后，在任务结束前运行 `powershell -NoProfile -ExecutionPolicy Bypass -File .\Tools\Sync-InterviewPrepToObsidian.ps1`。脚本以 SHA-256 清单跟踪已管理文件：只更新内容变化的文件，只删除清单中已管理且未被人工改动的旧文件，并保护目标目录中的未知笔记。
- 若 Obsidian 中的已管理副本被单独修改，脚本会报告冲突并停止对应覆盖/删除。先人工比较并把需要保留的内容合并回本权威源，再恢复目标文件与上次受管版本一致并重跑；不能用强制覆盖绕过冲突。
- 同步后再次运行同一脚本应得到零内容变更；任务报告必须包含同步数量、冲突、哈希一致性和失败信息。同步失败时不得声称知识库更新全部完成。
- `/learn/` 与 `.codex/` 不属于项目代码，不加入提交或 PR。
- 本目录只记录项目知识；不自动提高学习掌握度。掌握度必须来自真实讲解、练习、修改、排错或迁移证据。
