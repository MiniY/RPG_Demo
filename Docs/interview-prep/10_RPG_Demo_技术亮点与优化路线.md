# RPG_Demo 技术亮点与优化路线

## 1. 技术亮点的判断标准

“亮点”不等于代码复杂或文件多。至少满足两项：

- 解决过真实问题；
- 有清晰不变量；
- 有可解释的替代方案与取舍；
- 有自动化/人工证据；
- 可迁移到其他工程。

## 2. 亮点一：从随机地图到可提交世界

### 亮点

把地图拆成：

```text
Generate → Plan → Commit → Project → Materialize → Ready
```

并通过 GenerationId、Registry 和 Authority 保证代际一致性。

### 为什么有价值

- 防止候选失败破坏旧世界；
- 放置冲突在移动真实对象前发现；
- 对迟到回调有明确拒绝依据；
- 测试可以对阶段和不变量逐层验证。

### 优化方向

- 给每个 phase 增加耗时与失败原因结构化统计；
- 生成/规划失败输出可复现 Seed；
- 对 post-commit failure 设计显式恢复策略；
- 把大型 Controller 中的 phase 动作进一步封装。

## 3. 亮点二：TowerRun 入口检查点

### 亮点

没有尝试序列化所有 Unity 瞬时对象，而是定义稳定恢复边界：

- 地图由 Seed + 版本 + 配置重建；
- 玩家/背包/商店由纯数据应用；
- 恢复完成与 GameplayReady 对齐。

### 优化方向

- 引入 migration registry，支持有限的旧 Schema；
- 写入故障注入；
- 明确 Fog 是否属于入口记录；
- 为槽位增加可观测元数据，但不影响核心 Hash；
- 测试 Windows/macOS/Linux 文件替换差异。

## 4. 亮点三：本地文件写入协议

### 亮点

临时文件验证、备份、原子替换、正式复读、SHA-256 和 uncertain 分类，体现“文件 API 返回不等于业务提交完成”。

### 优化方向

- 多写者互斥；
- 文件锁超时与恢复；
- backup 轮换策略；
- 崩溃点故障注入矩阵；
- 平台文件系统语义验证。

## 5. 亮点四：业务事务与回滚

背包、商店、成长、TowerRun Apply 使用快照回滚，让跨多个状态源的操作具有原子语义。

### 优化方向

- 减少频繁深拷贝；
- 将通知统一延迟到提交后；
- 为 rollback failure 设计错误升级；
- 用不可变 Record/command result 降低隐式修改。

## 6. 亮点五：测试环境与机制匹配

项目不仅有 EditMode，还保留：

- PlayMode；
- 真实 GPU；
- 跨进程；
- 截图与人工审查。

### 优化方向

- 建立一条可重复本地验证脚本；
- 区分 assertion、runner、process 三类结果；
- 生成机器可读汇总；
- 控制 persistentDataPath 和测试数据清理；
- 对不稳定测试建立 retry 规则，但禁止用 retry 掩盖确定性 Bug。

## 7. 性能优化优先级

### P0：先测量

建立基线：

- 目标平台与分辨率；
- 地图尺寸；
- 语义对象数量；
- 背包物品数量；
- Profiler marker；
- P50/P95/P99；
- GC Alloc；
- 峰值内存；
- GameplayReady 总耗时。

没有基线，不把优化建议写成已完成成果。

### P1：地图加载

潜在热点：

- 噪声与全图多轮扫描；
- Placement 每类服务重复遍历；
- Tilemap 逐格写；
- 小地图纹理上传；
- 同帧 Materialize。

候选优化：

1. 缓存 terrain/可走/距离字段索引。
2. Placement 共享候选集合。
3. 批量 Tile 更新。
4. 将纯数据 Generate 放后台，Unity 投影留主线程。
5. 分帧 Materialize，并把 Ready 保持为锁定状态。

### P2：战斗查询

当前每次攻击搜索活动 `BaseDamageable`。

验证方法：

- 10/100/1000 目标；
- 每秒攻击次数；
- 搜索耗时和分配；
- 对比 `OverlapCircleNonAlloc` 与 Registry。

优化必须保持：

- 选择最近合法目标；
- Generation 过滤；
- 池化对象有效性；
- 前摇时目标失效处理。

### P3：UI

包裹刷新全量重建。

测试：

- 10/100/500 项；
- 打开面板首帧；
- 频繁拾取；
- GC；
- 滚动位置。

按收益选择 Pool、Keyed Diff 或 Virtualization。

### P4：保存

`GameSaveService` 高频深拷贝可能有成本。

先统计：

- 每秒调用次数；
- candidate 大小；
- 序列化是否实际发生；
- 攻击/体力恢复是否需要每次镜像。

可选：

- dirty flag；
- 批量提交；
- 只在一致边界捕获；
- 不可变小对象；
- 将体力瞬态从检查点持久状态中重新定义。

## 8. 可维护性优化

### 8.1 拆分大型 UI Controller

`TowerRunUiController` 同时处理流程面板、槽位、设置/音量和运行时视图构建，容易产生隐式状态。

建议 seam：

- `TowerRunFlowView`
- `TowerRunSlotView`
- `SettingsPanelController`
- `AudioSettingsPresenter`
- `TowerRunUiCompositionRoot`

当前尚未实施，不写成事实。

### 8.2 统一伤害接收接口

引入 `IDamageReceiver`，同时保留玩家/世界对象各自失败策略。

迁移步骤：

1. 先包装现有 `TakeDamage`。
2. 改攻击者依赖接口。
3. 加玩家与 Damageable contract tests。
4. 最后移除类型判断。

### 8.3 澄清 Runtime Save 命名

将 `GameSaveService` 职责重命名或拆分，避免与 SlotStore 混淆。必须先扫描所有调用者并保留迁移适配。

### 8.4 降低静态事件

Reward Pickup 使用场景级 collector/service，提升测试隔离和多玩家扩展。

### 9.1 按求职时间重新分组

- **求职前必须处理：** 最终工作树全量回归、TowerRun 人工流程、设置 UI 收口、Runner 挂起至少得到可复述结论。
- **求职前值得掌握但不一定实现：** 伤害接口迁移方案、地图/背包性能测量设计、存档 migration 思路。
- **简历投递后继续完善：** 包裹增量视图、结构化诊断面板、跨平台文件测试。
- **长期重构与扩展：** 多版本存档迁移、异步/分帧地图、职业/装备/Boss 等内容系统。

## 9.2 三项优先优化的标准决策记录

### A. 让验证基线可信

- **问题背景：** 测试结果跨多个提交，TowerRun EditMode 断言完成但进程挂起。
- **当前实现：** 有 EditMode、PlayMode、GPU、跨进程和定向 UI 记录。
- **改进目标：** 在最终提交上得到可重复、分层、带退出码的报告。
- **可选方案：** 只引用历史结果；手工逐项运行；建立统一脚本/报告。
- **推荐方案：** 先 fixture 二分修复/隔离挂起，再按层执行并保留环境与 SHA。
- **预计范围：** 测试基础设施、本地执行说明；不改业务语义。
- **实施步骤：** 二分 → 根因/隔离 → 全量 → 人工 checklist → 汇总。
- **兼容风险：** 为“让测试过”误改产品输入/焦点语义。
- **验证方法：** 断言、Runner、进程均成功；重复两次；工作树状态记录。
- **预期收益：** 面试和后续迭代不再依赖模糊的历史绿色结果。
- **面试价值：** 展示证据判断和质量保障。
- **优先级：** 求职前必须。

### B. 地图生成性能基线

- **问题背景：** 能指出多轮全图扫描和投影风险，但没有实际耗时数据。
- **当前实现：** 同步 Generate/Plan/Project/Materialize，逻辑正确性测试较强。
- **改进目标：** 确定真实瓶颈和可接受地图规模。
- **可选方案：** 直接多线程；只加总计时；按 phase 加 Profiler marker。
- **推荐方案：** 先按 phase 记录 P50/P95、GC、地图尺寸和 attempt，再决定索引/批量/后台化。
- **预计范围：** 诊断 marker、基准场景/测试、报告；第一阶段不改算法。
- **实施步骤：** 定义场景 → 基线 → 识别热点 → 单项优化 → 相同 Seed 回归。
- **兼容风险：** 测量代码影响结果；后台化破坏确定性或调用 Unity API。
- **验证方法：** 相同输入、相同输出不变量、优化前后统计。
- **预期收益：** 把“潜在风险”变成量化决策。
- **面试价值：** 展示先测量后优化。
- **优先级：** 求职前掌握方法，未必实现完整优化。

### C. 包裹增量刷新

- **问题背景：** 当前 `PackageGridUI.Refresh()` 销毁并重建全部 Slot。
- **当前实现：** 小规模简单可靠，但可能造成分配、布局重算和交互状态丢失。
- **改进目标：** 在物品规模增长时只更新变化项。
- **可选方案：** 保持现状；Slot Pool；以 rewardId keyed diff；虚拟列表。
- **推荐方案：** 先基准，再采用 Pool + keyed diff；只有非常大列表再虚拟化。
- **预计范围：** PackageGridUI、Slot 生命周期、Tooltip/选中状态、UI 测试。
- **实施步骤：** 建身份映射 → 复用/回收 → 更新数量 → 保持排序/滚动 → 回归。
- **兼容风险：** 池化 Slot 残留旧图标/事件；排序变化；删除选中项。
- **验证方法：** 10/100/500 项的耗时/GC；添加、删除、堆叠、排序、打开关闭。
- **预期收益：** 减少 UI 抖动和 GC，同时保持当前业务状态源不变。
- **面试价值：** 展示规模驱动、渐进式优化。
- **优先级：** 简历投递后完善。

## 10. 面试中的优化表达

推荐：

> 当前攻击目标查询是每次攻击扫描活动 Damageable；在当前原型规模可接受，但我会先用 10/100/1000 目标测主线程时间和分配，再决定用 NonAlloc 物理查询还是本代 Registry。优化必须保持最近目标和 Generation 过滤语义。

不推荐：

> 我会用对象池、多线程、ECS 全部优化掉。

后者没有指标、场景和正确性边界。
