# RPG_Demo 项目全景与总体介绍

## 0. 背景、动机与目标用户

`【历史记录】` 项目来源于 2D 像素 ARPG 的持续学习与作品集实践，使用 Tiny Swords 等资源逐步搭建玩家、怪物、背包、商店和地图系统；后续重点从“跟随教程完成单功能”转向“把多个系统整合为可验证的运行闭环”。

开发动机有两层：

1. 游戏层：做出探索、战斗、收集、成长、交易和楼层推进的可玩原型。
2. 工程层：练习 Unity 组件协作、数据流、生命周期、Git 分支整合、自动化测试与 AI 辅助开发。

目标用户是：

- 直接用户：喜欢俯视角像素 ARPG 和短流程楼层挑战的玩家；
- 当前现实用途：开发者本人用于 Unity 学习、代码掌握、作品集展示和求职面试。

`【待确认】` 当前没有发行、真实外部用户规模或商业运营证据，不能包装为已上线产品。

## 1. 项目一句话定位

`RPG_Demo` 是一个基于 Unity 2022.3 LTS 的俯视角 2D 像素风 ARPG 原型：玩家在确定性生成的地图中探索、战斗、收集与交易，并通过 TowerRun 楼层流程完成“进入楼层—击败目标—开启出口—保存检查点—进入下一层”的闭环。

`【已验证事实】` 当前唯一构建场景是 `Assets/Scenes/SampleScene.unity`，场景同时承载玩家、UI、遗留静态网格和 `RandomMapRuntime`；运行时由明确的 Authority（权威源）选择随机生成地图或旧静态地图。

## 2. 项目当前能力边界

| 领域 | 当前有证据支持的实现 | 不应夸大的边界 |
|---|---|---|
| 玩家 | Input System 输入、移动、方向、攻击、体力消耗/恢复；Monster 命中后红闪，其他已有伤害来源可击退 | 没有职业选择系统；攻击目标搜索仍较朴素 |
| 战斗 | 玩家攻击 `BaseDamageable`；怪物攻击 `PlayerDamageController`；共享伤害数据语义 | 接收者尚未统一成同一个伤害接口 |
| 怪物 AI | Patrol/Search/Chase/Attack/Return 状态机、视线检测、攻击前摇与冷却 | 不等于拥有复杂寻路、群体协作或行为树 |
| 奖励/背包 | 奖励请求先校验后拾取；背包变更失败可回滚；UI 网格与提示 | 红点是会话级规则，不是持久化的逐物品“未读”模型 |
| 商店 | 稳定商品 ID、库存、购买校验、背包和库存的原子式回滚 | 当前重点是购买；出售、回购、动态经济未实现 |
| 随机地图 | Seed 驱动、多噪声地形、连通性/道路/嵌套带、语义对象规划、雾和小地图 | 不是运行时无缝流式世界，也没有 NavMesh 路径系统 |
| TowerRun | 新冒险、三槽恢复、死亡选择、楼层出口、下一层、检查点兼容性 | 检查点保存楼层入口状态，不是战斗中任意时刻快照 |
| 持久化 | `TowerRunSlotStore` 三槽 JSON、临时文件验证、替换/备份、SHA-256 核对 | `GameSaveService` 当前仅为进程内数据服务，不再读写旧 `save.json` |
| 测试 | EditMode、PlayMode、GPU 图形测试、跨进程写入/读取测试 | 最近一次证据不是本次文档生成时重新执行的全量测试 |

## 4. 玩家可见的核心循环

```mermaid
flowchart LR
    A[选择新冒险或存档槽] --> B[生成/恢复楼层]
    B --> C[出生并绑定相机]
    C --> D[探索地图与小地图]
    D --> E[战斗/破坏/拾取]
    E --> F[背包、成长、商店]
    F --> G[击败本层全部目标]
    G --> H[出口与传送门解锁]
    H --> I[交互确认进入下一层]
    I --> J[捕获下一层入口检查点]
    J --> B
```

这里最重要的产品语义是：

- `【已验证事实】` 出口不是生成后立即可用，而是由本代地图的怪物目标全部失败后解锁。
- `【已验证事实】` 进入出口需要玩家在范围内主动按交互键；不是碰撞即自动切层。
- `【已验证事实】` 检查点描述“楼层入口”而非“当前战斗瞬间”，因此死亡恢复具有清晰、可重复的边界。

## 5. 软件结构的核心思想

### 5.1 逻辑数据与表现分离

随机地图首先产生 `MapData（地图逻辑数据）`，再由 `MapTilemapRenderer` 投影到 Tilemap。对象放置也先形成计划和占位记录，再移动真实场景对象。

这样做解决了三个问题：

1. 逻辑可在 EditMode 中测试，不依赖完整画面。
2. 小地图、出生、对象放置共享同一份逻辑真相。
3. 失败可在“提交”前被拒绝，减少半生成世界。

### 5.2 显式生命周期

地图整合不是一个布尔值，而是从 `Initialized` 经生成、规划、提交、投影、实例化、出生、重初始化、相机绑定、验证，最终到 `Ready` 的状态序列。

这让“地图已经画出来但玩家/相机/怪物还没准备好”不再被误判为可游玩。

### 5.3 事务式状态变更

背包、商店、成长和 TowerRun 恢复普遍采用：

```text
校验 → 捕获旧状态 → 应用候选状态 → 提交 → 失败则回滚 → 成功后通知 UI
```

这是 `Transaction（事务）` 的简化工程模型：不一定依赖数据库，但仍追求原子性和可恢复性。

### 5.4 稳定身份与兼容性

奖励、商店、商品、地图配置和生成版本使用稳定 ID。存档读取不只判断“JSON 能否解析”，还检查 Schema、生成器版本、配置身份、数值范围与 ID 唯一性。

## 6. 四种面试介绍版本

### 30 秒版本

> 我做的是一个 Unity 2D 俯视角 ARPG 原型。项目从玩家战斗、怪物状态机、背包和商店，演进到确定性随机地图和 TowerRun 楼层存档。技术上我重点关注了地图逻辑与 Tilemap 表现分离、运行时生成生命周期、事务式背包/商店变更，以及带兼容性校验和原子替换的三槽存档。大量实现由 Codex 辅助生成，我主要负责需求边界、方案判断、验收和复盘，所以面试中我会区分“能从源码和测试证明的事实”和“尚待验证的优化设想”。

### 1 分钟版本

> RPG_Demo 是 Unity 2022.3 的俯视角 2D ARPG 学习型原型。玩家可以探索随机地图、战斗、拾取奖励、使用背包和商店，并在 TowerRun 中击败本层目标、解锁出口、保存下一层入口检查点。地图不是直接随机画 Tile，而是先生成 `MapData`，再规划语义对象、提交、投影、出生玩家和绑定相机，全部完成后才发布 GameplayReady。背包和商店采用快照回滚，TowerRun 三槽存档则校验版本和稳定 ID，并通过临时文件、备份和写后 Hash 验证降低损坏风险。代码大量由 Codex 辅助，我负责需求和边界、方案取舍、验收、故障复现与学习复盘。

### 90 秒备用版本

> 项目是 Unity 2022.3 的 2D 像素风 ARPG。基础玩法包括 Input System 驱动的移动与攻击、体力和成长、怪物 Patrol/Search/Chase/Attack/Return 状态机、奖励拾取、背包和商店。项目后来把独立随机地图分支整合进主场景：生成器先产出 `MapData`，再经历规划、提交、Tilemap 投影、语义对象实例化、玩家出生、组件重初始化和相机绑定，只有全部验证完成才发布 GameplayReady。  
> 在此之上又增加 TowerRun 流程，存档不是随时保存战斗现场，而是保存楼层入口检查点。三槽存档会校验 Schema、生成器版本和稳定 ID，写入时先验证临时文件，再替换正式文件并重新读取、比对 SHA-256；失败时尽量恢复旧版本。项目有 EditMode、PlayMode、GPU 和跨进程持久化测试，不过画面手感和音频仍需要单独人工验收。

### 3 分钟版本

> RPG_Demo 最初是一个 Unity 2D 像素 ARPG 学习项目，逐步加入玩家四方向移动与攻击、体力和成长、怪物五状态 FSM、Damageable 与对象池、奖励拾取、背包和商店。  
> 随着系统增多，主要难点从“单功能能跑”变成“多个系统怎样共享同一世界并正确失败”。随机地图因此采用 `MapData` 作为逻辑真相：Seed 驱动高度、湿度、温度噪声，再经过连通性、出生保护、道路、嵌套和通道净空处理。商人、怪物、动物、植物和可破坏物不在各自 Start 中随便找位置，而是先产生 Placement Reservation，统一检查占位与可达性，通过后才 Commit 并移动真实对象。  
> 地图运行时还有显式生命周期。Tilemap 画完后仍要实体化对象、出生 canonical player、重置依赖、绑定相机和执行 TowerRun finalizer；只有这些不变量都成立才发布 GameplayReady。GenerationId 用来拒绝上一张地图迟到的回调；Commit 前失败会保留旧 Active Map/Registry，但 TowerRun 仍可能进入 Failure 并持有操作 Gate，不能简化为“玩家一定可以继续游玩旧世界”。  
> TowerRun 在此基础上定义新冒险、恢复、死亡选择和切层。它保存的是楼层入口检查点，不是任意战斗帧。三槽文件会验证 Schema、生成器版本、配置和稳定 ID，写入时使用 temp、backup、原子替换和写后 SHA-256 复读。背包和商店则使用快照回滚，保证购买不会出现扣钱没给货。  
> 验证上有 EditMode、PlayMode、真实 GPU 和跨进程测试，但我会明确测试时点：例如 216/216 地图 EditMode 和 16/16 PlayMode 对应特定提交；TowerRun EditMode 虽 21/21 断言通过，但 Runner 曾挂起，不能说全流程执行成功。大量代码由 Codex 辅助，因此我会用能否解释、复现、测试和修改来证明掌握，而不是声称全部手写。

### 5 分钟技术深入提纲

1. 产品循环：探索、战斗、收集、交易、成长、切层。
2. 地图：确定性 Seed、`MapData` 逻辑真相、连通性和通道宽度不变量。
3. 运行时整合：规划与提交分离，生命周期直到 GameplayReady。
4. 战斗与 AI：输入、体力、延迟命中、怪物 FSM、按伤害来源区分的玩家受击反馈和对象池。
5. 经济：奖励请求、背包事务、商店跨背包和库存回滚。
6. TowerRun：入口检查点、三槽存档、兼容性与写后验证。
7. 测试：哪些自动化通过、哪些只在历史版本通过、哪些仍需人工。
8. AI 边界：不把 AI 生成量伪装成个人手写量，重点证明自己能否解释、验证和修改。

## 8. 项目规模的正确表达

`【推断分析】` 这是一个具有多系统整合深度的学习型/作品集原型，而不是内容量完整的商业游戏。它的面试价值主要来自：

- 多个系统之间存在真实的数据和生命周期耦合；
- 遇到过可复述的错误、回归和修复；
- 有明确的兼容性、不变量、回滚与测试设计；
- Git 历史能展示从简单功能到深模块的演进。

它不应通过虚构关卡数量、用户规模、性能指标或商业上线经历来包装。
