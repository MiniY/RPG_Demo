### 已形成的链路

```text
RewardPickup
  → PlayerInventory 接受/拒绝
  → 背包数据变更
  → 保存候选状态
  → 成功后刷新 UI
  → 失败则保留地面奖励或回滚
```

商店则进一步把一次购买扩展为跨两个聚合状态的事务：

```text
校验金币/库存/容量
  → 捕获背包与库存快照
  → 扣金币
  → 加商品
  → 扣库存
  → 提交候选运行时状态
  → 失败全部回滚
```

### 用户验收证据

`【历史记录】` 商店正常流曾人工确认：100 金币，拾取后 108；花 5 金币购买肉后为 103，获得 2 个肉，库存剩 2，并能在当时的重新打开/重启流程中恢复。

### 当时未闭环的边界

`【历史记录】` 金币不足、售罄、最大数量、保存失败、快速连点等边界在当时的总结中仍属待验收。后续代码补强了部分事务和测试，但不能反推当时已完成所有人工验证。

### 经验

1. UI 显示不是状态源；背包和商店控制器才是状态源。
2. 地面物品必须在库存确认接受后再消失。
3. 交易成功通知应晚于提交，否则 UI 可能短暂显示未提交状态。
4. 稳定 `RewardId/ProductId/CatalogId` 比对象引用更适合保存。

### 架构演进

初期问题是“如何画一张随机地图”；后期问题变成“如何证明地图可玩，并让所有依赖系统共享同一逻辑真相”。

关键变化：

- 从直接写 Tilemap 转向 `MapData → Renderer`。
- 从单纯噪声分类转向连通性、出生保护、道路、嵌套带和通道宽度不变量。
- 小地图不读取屏幕像素，而读取 `MapData` 和探索状态。
- 简单装饰独立生成，避免把地形语义和表现细节绑死。

`【历史记录】` 分支阶段曾记录 66 个 EditMode 测试通过，并使用 Seed `839235445`、`613580675` 进行用户复测。该数字属于当时分支，不是当前测试总数。

## 5. 阶段四：怪物 AI 并行开发

### 设计

怪物行为拆为：

- `Perception（感知）`：距离与视线；
- `Decision（决策）`：Patrol/Search/Chase/Attack/Return；
- `Movement（移动）`：朝目标或巡逻点移动；
- `Attack（攻击）`：前摇、方向锁定、命中复核、冷却；
- `Presentation（表现）`：动画与受击反馈。

### 复盘

### 最大的工程转变

旧问题：

> 随机地图能生成，但主场景中的玩家、相机、怪物、商人、动物、植物、破坏物和 UI 何时、以什么顺序迁移到新地图？

解决方式：

1. 引入 `MapRuntimeContext` 统一记录本次 Generation。
2. 用 `MapIntegrationOrchestrator` 控制重试、规划、提交和投影。
3. 为每类语义对象实现放置服务。
4. 先规划 `Reservation（占位）`，通过后才移动真实对象。
5. 使用 `GenerationId（生成代 ID）` 拒绝过期回调和旧对象。
6. 玩家出生、组件重置、相机绑定、最终验证全部成功后才发布 GameplayReady。

### 典型事故

`92f84e8` 说明 Unity 资源 GUID 和 `.meta` 文件不是附属品。格式损坏会使引用关系失真；修复时必须同时理解文件系统状态和 Unity Asset Database（资源数据库）。

## 7. 阶段六：Damageable 奖励闭环与代际权威

### 关键提交

- `b8e27c9`：火炬奖励映射与 generation-scoped 奖励。
- `e7aff9f`：`BaseDamageable` 只接受唯一活动 RandomGenerated authority；失败再生成时保留当前 Generation 的奖励生命周期。地图 Pending/Active 与失败保留机制更早由 `5df3b40`、`2bfd4e1`、`392b973` 建立和强化。
- `d9f60d6`：PR #2 合并。

### 解决的问题

如果旧一代地图上的物体在新一代生成后才触发死亡/奖励，奖励可能污染新世界。项目通过 Generation 所有权和 `GenerationScopedRewardLifetime` 把奖励绑定到正确代。

另一个关键决策是：

> 新地图生成失败时，不应先销毁当前可玩的旧世界。

因此生成过程在 Commit 前尽量保持旧状态，失败不会自动把用户留在半生成空场景。

### 产品语义

- 新冒险从基线状态开始。
- 恢复读取某个入口检查点。
- 本层目标全部死亡后，出口和传送门才可用。
- 玩家主动交互进入下一层。
- 切层先捕获 carry state，再生成下一层入口检查点。
- 死亡时进入 DeathChoice，可恢复或新开。

### 为什么不是“普通 Save/Load”

TowerRun 把保存语义绑定到明确的流程状态，而不是任何时刻序列化所有场景对象。这样牺牲了“任意时刻继续”，换来：

- 边界清晰；
- 恢复可重复；
- 不必保存每个临时投射物、动画时间和对象池内部状态；
- 更容易验证兼容性。

## 11. 总体经验

### 做得较好的

- 逐步把“功能代码”深化成具有生命周期、稳定身份、不变量和失败语义的模块。
- 不是只依赖单元测试，还覆盖 PlayMode、真实 GPU 和跨进程文件持久化。
- 对历史事实保留证据，能识别文档过时和实现语义变化。

### 仍需加强的

- 性能结论缺少 Profiler、帧耗、GC、分配和生成耗时的保留数据。
- 视觉、音频、手感和极端分辨率的人工验收记录不完整。
- 部分系统接口仍分裂，如世界对象与玩家的伤害接收。
- UI 有重建整个网格等可优化路径。
- 个人掌握度不能从 AI 生成代码量和测试通过数推导，必须通过讲解、修改和排错重新建立证据。
